## Project

A data-collection instrument: a native iOS app captures location and radio (BLE/network-metadata) signals, queues them offline, and syncs them in batches to a Go backend for cross-device/location collation. See `/Users/louisnaber/.claude/plans/i-need-to-create-glistening-elephant.md` for the full architecture plan.

- `backend/signals-backend/` — Go + Postgres ingestion API.
- `ios/SignalKit/` — Swift Package with the capture/queue/sync core (models, capturers, GRDB-backed offline queue, sync engine).
- `ios/Signals/` — the app target (onboarding/consent screen, capture status UI, `AppDelegate`/`SignalsApp` wiring). Consumes `SignalKit` as a local package dependency.
- `ios/Signals.xcodeproj` — generated by `xcodegen` from `ios/project.yml`; **don't hand-edit the `.xcodeproj`**, edit `project.yml` and re-run `xcodegen generate` from `ios/`.

## Backend: build, run, test

```sh
cd backend/signals-backend
go build ./...
go vet ./...

# Local Postgres (note: mapped to host port 5433, not 5432 -- a native

cd deploy && docker compose up -d

DATABASE_URL="postgres://signals:signals@localhost:5433/signals?sslmode=disable" \
ADMIN_KEY="dev-admin-key" \

```

No Go test files exist yet (verified via manual `curl` against `/v1/devices` and `/v1/signals/batches` instead — see the plan's Verification section for the exact idempotency/auth checks worth re-running after backend changes).

## iOS: build, test

```sh
cd ios/SignalKit
swift build && swift test                                    # macOS host, fast inner loop
xcodebuild -scheme SignalKit -destination "generic/platform=iOS Simulator" build
xcodebuild -scheme SignalKit -destination "platform=iOS Simulator,name=iPhone 17" test
```

`Package.swift` declares both `.iOS(.v16)` and `.macOS(.v13)` platforms — the macOS target exists purely so `swift build`/`swift test` run locally without a simulator; the app itself is iOS-only. Code behind `#if os(iOS)` (CoreTelephony, BackgroundTasks) only typechecks on an iOS build/test run, not the macOS one — verify both when touching `NetworkMetadataCapturer` or `BackgroundTaskCoordinator`.

### App target

```sh
cd ios
xcodegen generate      # regenerate Signals.xcodeproj after editing project.yml
xcodebuild -project Signals.xcodeproj -scheme Signals -destination "generic/platform=iOS Simulator" build
```

The app has an in-app provisioning flow (`ProvisioningView`), shown after onboarding whenever no API key is stored: a "paste a pre-provisioned key" path that ships in every build, plus a `#if DEBUG`-only "provision via admin key" path that calls `POST /v1/devices` directly for fast local iteration. `SIGNALS_API_BASE_URL` / `SIGNALS_API_KEY` scheme environment variables (`DevConfig.swift`) remain a quick fallback for dev builds that skip the UI entirely.

Once "When In Use" location is granted, `ContentView` shows a background-capture banner (`BackgroundUpgradeView`) explaining the "Always" upgrade before triggering the system prompt — a distinct, explicitly-justified ask per the plan, not bundled into the initial request. `CaptureController.locationAuthorizationStatus` tracks the live `CLAuthorizationStatus` via `LocationCapturer.onAuthorizationChange`; `enableBackgroundUpdates()` is only called once "Always" is actually granted.

### UI tests

```sh
cd ios
xcrun simctl spawn <device-id> defaults delete com.signals.app   # see gotcha below -- required before each run
xcodebuild -project Signals.xcodeproj -scheme Signals -destination "platform=iOS Simulator,id=<device-id>" test -only-testing:SignalsUITests
```

`SignalsUITests/ProvisioningFlowUITests` drives the real flow (onboarding tap → admin-key provisioning → capture screen) against a live backend, so `backend/signals-backend` must be running locally at `http://localhost:8080` with `ADMIN_KEY=dev-admin-key` before running it. `SignalsUITests/BackgroundUpgradeFlowUITests` drives the "Always" location upgrade flow and handles the real system location alerts via `addUIInterruptionMonitor` — no backend dependency.

## Non-obvious constraints

- **No real WiFi scanning on iOS.** There is no public API for third-party apps to enumerate nearby SSIDs/BSSIDs (would require an Apple-granted `NEHotspotHelper` entitlement). `NetworkMetadataCapturer` only reports the *currently associated* network plus carrier/radio-tech — it is deliberately named `network_metadata`, not `wifi_scan`, in both the Swift payload type and the backend's `signal_type` column. Don't "fix" this to attempt broader scanning; it isn't available.
- **Background BLE scanning is unreliable for a wildcard scan.** `BLEScanCapturer` accepts an optional `serviceUUIDsToScan` allow-list; per Apple's documented behavior, scanning for all services (`nil`) in the background frequently misses peripherals. If a deployment needs reliable background discovery, it must scan for a curated set of known service UUIDs, not `nil`.
- **BLE peripheral UUIDs are session-random**, not stable hardware identifiers — don't treat `ble_advertisement.peripheral_uuid` as a durable device fingerprint in analysis.
- **`signals` table is partitioned by `captured_at`** with a single `signals_default` catch-all partition for now; there's no monthly-partition creation job yet (noted as a step-13 backend task in the plan, not yet built).
- **Idempotency depends on the client, not the server, generating IDs.** `SignalRecord.id` and each sync batch's `batch_id` are generated at capture/batch-build time (client-side), not at send time — this is what makes retries safe (`ON CONFLICT DO NOTHING` server-side). Don't regenerate these IDs on retry.
- **Port 5432 is taken locally.** A native Homebrew Postgres already listens on `localhost:5432` on this dev machine, ahead of Docker's port-forward for the same port. `deploy/docker-compose.yml` maps the dev Postgres container to host port **5433** to avoid silently talking to the wrong database — keep this in mind if compose files are ever consolidated or `DATABASE_URL` is copy-pasted elsewhere.
- **`Application Support` doesn't exist in a fresh app container.** `CaptureController` creates it (`FileManager...createDirectory`) before opening the GRDB database there — this was a real crash on first launch (SQLite error 14, "unable to open database file") until fixed. Don't remove that `createDirectory` call.
- **`BGTaskScheduler.register` must run before `application(_:didFinishLaunchingWithOptions:)` returns.** That's why `CaptureController` (which registers the background task in its own `init`) is created as a stored property of `AppDelegate` and wired in via `@UIApplicationDelegateAdaptor`, not as a `@StateObject` on the SwiftUI `App` struct — the latter doesn't reliably guarantee that ordering.
- **`simctl uninstall` does not clear `UserDefaults`/`NSUserDefaults` between test runs.** cfprefsd caches an app's preferences domain independent of its container, so a plain uninstall+reinstall (what `xcodebuild test` does) can leave a stale `hasAcknowledgedConsent`/etc. from a previous run, silently skipping onboarding in a UI test even though `AppDelegate`'s `-uitesting-reset` handling calls `UserDefaults.standard.removeObject`. Run `xcrun simctl spawn <device-id> defaults delete com.signals.app` before each UI test invocation — this was a real, reproduced failure (`ProvisioningFlowUITests` landed straight on the provisioning screen instead of onboarding until this was added), not a hypothetical.
- **The provisioning admin-key path is gated `#if DEBUG`, not a runtime flag.** `ProvisioningView` and `CaptureController.provisionViaAdminKey` compile out of release builds entirely -- the admin key itself is always user-typed, never embedded, but a release build still shouldn't carry the *capability* to call the admin-protected endpoint at all. Don't change this to a runtime toggle (e.g. a settings switch); that would leave the capability shippable, just hidden.
