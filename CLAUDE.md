# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A data-collection instrument: a native iOS app captures location and radio (BLE/network-metadata) signals, queues them offline, and syncs them in batches to a Go backend for cross-device/location collation. See `/Users/louisnaber/.claude/plans/i-need-to-create-glistening-elephant.md` for the full architecture plan.

- `backend/signals-backend/` — Go + Postgres ingestion API.
- `ios/SignalKit/` — Swift Package with the capture/queue/sync core (models, capturers, GRDB-backed offline queue, sync engine).
- `ios/Signals/` — the app target (onboarding/consent screen, capture status UI, `AppDelegate`/`SignalsApp` wiring). Consumes `SignalKit` as a local package dependency.
- `ios/Signals.xcodeproj` — generated by `xcodegen` from `ios/project.yml`; **don't hand-edit the `.xcodeproj`**, edit `project.yml` and re-run `xcodegen generate` from `ios/`.

## Backend: build, run, test

```sh
cd backend/signals-backend
go build ./...
go vet ./...

# Local Postgres (note: mapped to host port 5433, not 5432 -- a native
# Homebrew Postgres on this machine already owns 5432 on localhost)
cd deploy && docker compose up -d
docker exec -i deploy-postgres-1 psql -U signals -d signals < ../migrations/0001_init.sql

DATABASE_URL="postgres://signals:signals@localhost:5433/signals?sslmode=disable" \
ADMIN_KEY="dev-admin-key" \
go run ./cmd/server
```

No Go test files exist yet (verified via manual `curl` against `/v1/devices` and `/v1/signals/batches` instead — see the plan's Verification section for the exact idempotency/auth checks worth re-running after backend changes).

## Backend: admin observation viewer

`GET /admin/signals` (HTML) and `GET /admin/signals.json` (filters: `device_id`, `signal_type`; pagination: `limit`/`offset`) are protected by HTTP Basic auth (any username, password = `ADMIN_KEY`) — reuses the same admin key as `POST /v1/devices` rather than adding new infra, so it's live at `https://signals-api-dev.fly.dev/admin/signals` and `https://signals-api-prod.fly.dev/admin/signals` as soon as the backend is deployed. Distinct from `adminAuth` (the `X-Admin-Key` header middleware used by device provisioning): Basic auth lets the browser handle the credential prompt/caching natively for a page view, where a custom header isn't practical.

## Backend: deployment (Fly.io + GitHub Actions)

Two separate Fly apps, `signals-api-dev` and `signals-api-prod`, each with their own Fly Postgres — configs live at `backend/signals-backend/deploy/fly.dev.toml` / `fly.prod.toml`. `.github/workflows/backend-ci.yml` runs `go build`/`go vet`/`go test` on every push/PR touching the backend; `.github/workflows/backend-deploy.yml` deploys on push to `dev` (→ dev app) or `main` (→ prod app), or manually via `workflow_dispatch`. Dev scales to zero when idle (`min_machines_running = 0`); prod stays warm (`min_machines_running = 1`).

**One-time setup (run locally, not from Claude Code — these hit your Fly account/billing):**

```sh
brew install flyctl   # or: curl -L https://fly.io/install.sh | sh
fly auth login

cd backend/signals-backend
fly apps create signals-api-dev
fly apps create signals-api-prod

fly postgres create --name signals-db-dev --region iad
fly postgres attach signals-db-dev --app signals-api-dev   # sets DATABASE_URL secret on the app

fly postgres create --name signals-db-prod --region iad
fly postgres attach signals-db-prod --app signals-api-prod

fly secrets set ADMIN_KEY="$(openssl rand -hex 32)" --app signals-api-dev
fly secrets set ADMIN_KEY="$(openssl rand -hex 32)" --app signals-api-prod

# Run the migration against each new DB (get the connection string via `fly postgres connect -a signals-db-dev`, etc.)
psql "<dev-connection-string>" < migrations/0001_init.sql
psql "<prod-connection-string>" < migrations/0001_init.sql

# CI/CD auth: create an org-wide token so one secret can deploy both apps
fly tokens create org -x 999999h
gh secret set FLY_API_TOKEN --body "<token>"
```

Optionally add GitHub `dev`/`prod` [environments](https://docs.github.com/actions/deployment/targeting-different-environments/using-environments-for-deployment) (Settings → Environments) to gate `prod` deploys behind manual approval — the deploy workflow already targets `environment: prod`/`dev` per branch, so adding protection rules there is enough, no workflow changes needed.

## iOS: build, test

```sh
cd ios/SignalKit
swift build && swift test                                    # macOS host, fast inner loop
xcodebuild -scheme SignalKit -destination "generic/platform=iOS Simulator" build
xcodebuild -scheme SignalKit -destination "platform=iOS Simulator,name=iPhone 17" test
```

`Package.swift` declares both `.iOS(.v16)` and `.macOS(.v13)` platforms — the macOS target exists purely so `swift build`/`swift test` run locally without a simulator; the app itself is iOS-only. Code behind `#if os(iOS)` (CoreTelephony, BackgroundTasks) only typechecks on an iOS build/test run, not the macOS one — verify both when touching `NetworkMetadataCapturer` or `BackgroundTaskCoordinator`.

### App target

```sh
cd ios
xcodegen generate      # regenerate Signals.xcodeproj after editing project.yml
xcodebuild -project Signals.xcodeproj -scheme Signals -destination "generic/platform=iOS Simulator" build
```

The app has an in-app provisioning flow (`ProvisioningView`), shown after onboarding whenever no API key is stored: a "paste a pre-provisioned key" path that ships in every build, plus a `#if DEBUG`-only "provision via admin key" path that calls `POST /v1/devices` directly for fast local iteration. It's also reachable any time via the "Device connection" button on the capture screen (`ContentView`), not just on first launch -- needed because a stored key is scoped to whichever backend issued it, so switching backends (e.g. local -> hosted dev) needs re-provisioning even though a key is already present. `DevConfig.apiBaseURL` (`DevConfig.swift`) defaults to the hosted Fly dev backend (`https://signals-api-dev.fly.dev`); override `SIGNALS_API_BASE_URL` / `SIGNALS_API_KEY` via the Xcode scheme's environment variables to point a debug build at a local backend instead (`http://localhost:8080` on the Simulator, the Mac's LAN IP on a real device).

Once "When In Use" location is granted, `ContentView` shows a background-capture banner (`BackgroundUpgradeView`) explaining the "Always" upgrade before triggering the system prompt — a distinct, explicitly-justified ask per the plan, not bundled into the initial request. `CaptureController.locationAuthorizationStatus` tracks the live `CLAuthorizationStatus` via `LocationCapturer.onAuthorizationChange`; `enableBackgroundUpdates()` is only called once "Always" is actually granted.

### UI tests

```sh
cd ios
xcrun simctl spawn <device-id> defaults delete com.naberconsulting.signals.app   # see gotcha below -- required before each run
xcodebuild -project Signals.xcodeproj -scheme Signals -destination "platform=iOS Simulator,id=<device-id>" test -only-testing:SignalsUITests
```

`SignalsUITests/ProvisioningFlowUITests` drives the real flow (onboarding tap → admin-key provisioning → capture screen) against a live backend, so `backend/signals-backend` must be running locally at `http://localhost:8080` with `ADMIN_KEY=dev-admin-key` before running it. `SignalsUITests/BackgroundUpgradeFlowUITests` drives the "Always" location upgrade flow and handles the real system location alerts via `addUIInterruptionMonitor` — no backend dependency.

## Non-obvious constraints

- **No real WiFi scanning on iOS.** There is no public API for third-party apps to enumerate nearby SSIDs/BSSIDs (would require an Apple-granted `NEHotspotHelper` entitlement). `NetworkMetadataCapturer` only reports the *currently associated* network plus carrier/radio-tech — it is deliberately named `network_metadata`, not `wifi_scan`, in both the Swift payload type and the backend's `signal_type` column. Don't "fix" this to attempt broader scanning; it isn't available.
- **Background BLE scanning is unreliable for a wildcard scan.** `BLEScanCapturer` accepts an optional `serviceUUIDsToScan` allow-list; per Apple's documented behavior, scanning for all services (`nil`) in the background frequently misses peripherals. If a deployment needs reliable background discovery, it must scan for a curated set of known service UUIDs, not `nil`.
- **BLE peripheral UUIDs are session-random**, not stable hardware identifiers — don't treat `ble_advertisement.peripheral_uuid` as a durable device fingerprint in analysis.
- **`signals` table is partitioned by `captured_at`** with a single `signals_default` catch-all partition for now; there's no monthly-partition creation job yet (noted as a step-13 backend task in the plan, not yet built).
- **Idempotency depends on the client, not the server, generating IDs.** `SignalRecord.id` and each sync batch's `batch_id` are generated at capture/batch-build time (client-side), not at send time — this is what makes retries safe (`ON CONFLICT DO NOTHING` server-side). Don't regenerate these IDs on retry.
- **Port 5432 is taken locally.** A native Homebrew Postgres already listens on `localhost:5432` on this dev machine, ahead of Docker's port-forward for the same port. `deploy/docker-compose.yml` maps the dev Postgres container to host port **5433** to avoid silently talking to the wrong database — keep this in mind if compose files are ever consolidated or `DATABASE_URL` is copy-pasted elsewhere.
- **`Application Support` doesn't exist in a fresh app container.** `CaptureController` creates it (`FileManager...createDirectory`) before opening the GRDB database there — this was a real crash on first launch (SQLite error 14, "unable to open database file") until fixed. Don't remove that `createDirectory` call.
- **`BGTaskScheduler.register` must run before `application(_:didFinishLaunchingWithOptions:)` returns.** That's why `CaptureController` (which registers the background task in its own `init`) is created as a stored property of `AppDelegate` and wired in via `@UIApplicationDelegateAdaptor`, not as a `@StateObject` on the SwiftUI `App` struct — the latter doesn't reliably guarantee that ordering.
- **`simctl uninstall` does not clear `UserDefaults`/`NSUserDefaults` between test runs.** cfprefsd caches an app's preferences domain independent of its container, so a plain uninstall+reinstall (what `xcodebuild test` does) can leave a stale `hasAcknowledgedConsent`/etc. from a previous run, silently skipping onboarding in a UI test even though `AppDelegate`'s `-uitesting-reset` handling calls `UserDefaults.standard.removeObject`. Run `xcrun simctl spawn <device-id> defaults delete com.naberconsulting.signals.app` before each UI test invocation — this was a real, reproduced failure (`ProvisioningFlowUITests` landed straight on the provisioning screen instead of onboarding until this was added), not a hypothetical.
- **The provisioning admin-key path is gated `#if DEBUG`, not a runtime flag.** `ProvisioningView` and `CaptureController.provisionViaAdminKey` compile out of release builds entirely -- the admin key itself is always user-typed, never embedded, but a release build still shouldn't carry the *capability* to call the admin-protected endpoint at all. Don't change this to a runtime toggle (e.g. a settings switch); that would leave the capability shippable, just hidden.
- **`SignalStore` requeues stale `.uploading` rows on init.** `claimBatch` moves rows out of `.pending` before the network call; if the app crashes or is killed mid-upload, those rows have no in-flight tracking once the process exits. `SignalStore.init` calls `recoverStaleUploads()` unconditionally so they aren't silently stuck forever -- don't remove this on the assumption `SyncEngine`'s `markFailed` covers it, since `markFailed` only runs on a definite network response, not a crash.
- **`SyncEngine` prunes uploaded rows itself; nothing else calls `pruneUploaded`.** It runs after every sync pass (`defer` in `runSyncLoop`), deleting `.uploaded` rows older than 48h, so local DB growth is bounded independent of upload volume. `SignalStore.pruneUploaded` is `public` only because `SignalStoreTests` calls it directly -- app code should never need to call it itself.
- **Connectivity-loss/recovery tests use a stubbed `URLProtocol`, not real airplane-mode toggling.** `SyncEngineTests` (`ios/SignalKit/Tests/SignalKitTests/SyncEngineTests.swift`) simulates offline/online transitions deterministically via `StubURLProtocol` injected through `APIClient`'s `session` parameter -- toggling actual simulator/device airplane mode isn't scriptable for CI. If you need to verify real on-device connectivity behavior, that still has to be done manually.
- **`CaptureController` triggers a sync pass on `UIApplication.didBecomeActiveNotification`.** `SyncEngine`'s only other triggers are an `NWPathMonitor` connectivity *change* and the manual "Sync now" button -- if the network never actually drops while the app is backgrounded (the common case), nothing else prompts a sync when the app is reopened, so records captured in the background would sit queued indefinitely. This was a real gap found via on-device background testing (foreground-captured records synced fine; backgrounded ones didn't flush until this observer was added), not a hypothetical. Don't remove the observer on the assumption `NWPathMonitor` already covers "app came back" -- it only fires on state *transitions*.
- **Real-device builds need a bundle ID that isn't already registered to someone else** (`com.signals.app` was taken; the app now ships as `com.naberconsulting.signals.app`) and require an initial USB pairing before Xcode can find the device over WiFi (`Window → Devices and Simulators` → check "Connect via network" once cabled) -- WiFi-only, without ever cabling, the device silently never shows up.
- **`SyncEngine`'s backoff retry no longer blocks the queue with `Thread.sleep`.** A failed pass used to sleep synchronously (up to the 10-minute cap) before releasing `isSyncing`, which meant a manual "Sync now" tap or the foreground trigger arriving during that window silently no-op'd against the `isSyncing` guard -- this was a real, reproduced bug on a real device (repeated taps had zero effect for minutes at a time). Failed passes now call `scheduleRetry(after:)`, which releases `isSyncing` immediately and schedules the retry via `asyncAfter` instead -- don't reintroduce a blocking sleep here.
- **`SyncEngine.onPassCompleted` exists because polling queue state right after `triggerSync()` is unreliable.** `triggerSync()` only dispatches the pass asynchronously and returns immediately, so `CaptureController.syncNow()` calling `refreshPendingCount()` right after it reflected stale, pre-sync state -- on a real device this looked like "Sync now does nothing" even when the upload had actually succeeded. `CaptureController` now also refreshes the count from the `onPassCompleted` callback once the pass actually finishes; don't remove the immediate `refreshPendingCount()` call in `syncNow()` either, since it still gives instant feedback for the common case where nothing was pending.
- **`xcodegen generate` can leave a stale project with no schemes for `Signals`/`SignalsUITests`** if the previous `.xcodeproj` is regenerated in place after certain edits (observed after editing `project.yml` mid-session) -- `xcodebuild -list` then shows only the SPM package schemes (`SignalKit`, `GRDB-Package`). Fix: `rm -rf Signals.xcodeproj` before re-running `xcodegen generate` rather than debugging a partial regeneration.
