# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A data-collection instrument: a native iOS app captures location and radio (BLE/network-metadata) signals, queues them offline, and syncs them in batches to a Go backend for cross-device/location collation. See `/Users/louisnaber/.claude/plans/i-need-to-create-glistening-elephant.md` for the full architecture plan.

- `backend/signals-backend/` — Go + Postgres ingestion API.
- `ios/SignalKit/` — Swift Package with the capture/queue/sync core (models, capturers, GRDB-backed offline queue, sync engine).
- `ios/Signals/` — the app target (onboarding/consent screen, capture status UI, `AppDelegate`/`SignalsApp` wiring). Consumes `SignalKit` as a local package dependency.
- `ios/Signals.xcodeproj` — generated by `xcodegen` from `ios/project.yml`; **don't hand-edit the `.xcodeproj`**, edit `project.yml` and re-run `xcodegen generate` from `ios/`.
- `android/` — native Kotlin/Compose app mirroring the iOS capture→queue→sync pipeline against the same backend, plus Android-only captures iOS has no API for (nearby Wi-Fi BSSIDs, BLE advertiser MACs, cell-tower identities). See "Android: build, test".

## Backend: admin observation viewer

`GET /admin/signals` (HTML) and `GET /admin/signals.json` (filters: `device_id`, `signal_type`; pagination: `limit`/`offset`) are protected by HTTP Basic auth (any username; password = either `ADMIN_KEY` or the separate read-only `VIEWER_KEY`) — live at `https://signals-api-dev.fly.dev/admin/signals` and `https://signals-api-prod.fly.dev/admin/signals` as soon as the backend is deployed. Distinct from `adminAuth` (the `X-Admin-Key` header middleware used by device provisioning): Basic auth lets the browser handle the credential prompt/caching natively for a page view, where a custom header isn't practical. `VIEWER_KEY` exists so viewer access can be shared with someone (e.g. a collaborator who just wants to browse observations) without handing out `ADMIN_KEY`, which can also provision new devices via `POST /v1/devices` — it's optional (`envOrDefault`, unset = viewer login disabled) and independently rotatable via `fly secrets set VIEWER_KEY=... --app <app>`.

`GET /admin/signals/heatmap` (HTML) and `GET /admin/signals/heatmap.json` (same filters plus `precision`, a lat/lon rounding decimal-place count from 1-6, default 3 ≈100m grid cells) sit in the same `adminBasicAuth` route group and render observation density as a Leaflet heat layer. `store.HeatmapPoints` groups located signals into a `round(lat, precision), round(lon, precision)` grid server-side rather than shipping every raw point to the browser. Unlike the table viewer, the heat map page (`internal/api/heatmap_page.go`) isn't fully self-contained -- it loads Leaflet + `leaflet.heat` from a CDN, which is a wash given rendering an actual map already means fetching OpenStreetMap tile images over the network regardless.

`GET /admin/ai` (HTML), `GET /admin/ai/summary.json` (filters: `device_id`, `signal_type`, `since`, `until`), and `POST /admin/ai/ask` (same filters plus a JSON body `question`, capped at 500 chars) sit in the same `adminBasicAuth` group and provide a natural-language summary/Q&A interface over observations, backed directly by the Anthropic API (`internal/llm/client.go` — a minimal `net/http` client, not the full SDK, since this is the repo's only outbound-HTTP call site) via `ANTHROPIC_API_KEY` (optional; `envOrDefault`, unset = both endpoints return `503 ai_not_configured` rather than the server failing to start) and `ANTHROPIC_MODEL` (default `claude-haiku-4-5-20251001`, the cheapest current model — deliberate, since every summary/question is a live paid API call). Both handlers build their LLM context from `store.SignalStats` (aggregate counts by type/device, date range, and `tracker_tags_by_distinct_device` — counts of classified tracker tags by distinct advertiser, computed with a `payload->>'tag_type'` JSONB aggregate, the one place the AI context reflects payload contents at all, and still only as counts) plus the top 5 `HeatmapPoints` cells — **never raw signal payloads** — so prompt size and cost stay bounded regardless of how much data exists; `handleAIAsk`'s system prompt also instructs the model to answer only from that aggregate data and say so if it can't, rather than fabricate specifics. Rotate the key via `fly secrets set ANTHROPIC_API_KEY=... --app <app>`.

## Backend: QR device provisioning

`GET /admin/provision/qr` (HTML, in the `adminBasicAuth` group — `internal/api/handlers_provision.go`) is the zero-typing way to connect a device, built because both prior paths (paste an api key / type the admin key) force a long secret to be entered *on the phone*, which is impractical on a borrowed device. Each page load provisions a fresh device (`UpsertDevice` with a new `device_id` + `generateAPIKey`) and renders a QR encoding a `signals://connect?base=<public-base>&device_id=<id>&key=<apiKey>` deep link. The operator opens the page in a browser on a real computer (Basic auth handles the admin credential once), and the target phone scans the QR with its **stock camera app** — no in-app scanner, no camera permission. `base` is derived from the request `Host` + `X-Forwarded-Proto` (so it's correct behind Fly's TLS terminator). The QR carries a device bearer token, so the page is sensitive (already behind `adminBasicAuth`); a pairing-code flow would keep the token out of the QR at the cost of backend session state — deliberately not built. The link string is `json.Marshal`ed before embedding in the page's JS (escapes `&`→`&` etc.), and the QR itself renders client-side via a CDN `qrcodejs` (same CDN-on-admin-pages tradeoff as the heatmap page).

## Backend: deployment (Fly.io + GitHub Actions)

Two separate Fly apps, `signals-api-dev` and `signals-api-prod`, each with their own Fly Postgres — configs live at `backend/signals-backend/deploy/fly.dev.toml` / `fly.prod.toml`. `.github/workflows/backend-ci.yml` runs `go build`/`go vet`/`go test` on every push/PR touching the backend; `.github/workflows/backend-deploy.yml` deploys on push to `dev` (→ dev app) or `main` (→ prod app), or manually via `workflow_dispatch`. Dev scales to zero when idle (`min_machines_running = 0`); prod stays warm (`min_machines_running = 1`).

**One-time setup (run locally, not from Claude Code — these hit your Fly account/billing):**

```sh
brew install flyctl   # or: curl -L https://fly.io/install.sh | sh
fly auth login

cd backend/signals-backend
fly apps create signals-api-dev
fly apps create signals-api-prod

fly postgres create --name signals-db-dev --region iad
fly postgres attach signals-db-dev --app signals-api-dev   # sets DATABASE_URL secret on the app

fly postgres create --name signals-db-prod --region iad
fly postgres attach signals-db-prod --app signals-api-prod

fly secrets set ADMIN_KEY="$(openssl rand -hex 32)" --app signals-api-dev
fly secrets set ADMIN_KEY="$(openssl rand -hex 32)" --app signals-api-prod

# Run the migration against each new DB (get the connection string via `fly postgres connect -a signals-db-dev`, etc.)
psql "<dev-connection-string>" < migrations/0001_init.sql
psql "<prod-connection-string>" < migrations/0001_init.sql

# CI/CD auth: create an org-wide token so one secret can deploy both apps
fly tokens create org -x 999999h
gh secret set FLY_API_TOKEN --body "<token>"
```

Optionally add GitHub `dev`/`prod` [environments](https://docs.github.com/actions/deployment/targeting-different-environments/using-environments-for-deployment) (Settings → Environments) to gate `prod` deploys behind manual approval — the deploy workflow already targets `environment: prod`/`dev` per branch, so adding protection rules there is enough, no workflow changes needed.

## iOS: build, test

```sh
cd ios/SignalKit
swift build && swift test                                    # macOS host, fast inner loop
xcodebuild -scheme SignalKit -destination "generic/platform=iOS Simulator" build
xcodebuild -scheme SignalKit -destination "platform=iOS Simulator,name=iPhone 17" test
```

`Package.swift` declares both `.iOS(.v16)` and `.macOS(.v13)` platforms — the macOS target exists purely so `swift build`/`swift test` run locally without a simulator; the app itself is iOS-only. Code behind `#if os(iOS)` (CoreTelephony, BackgroundTasks) only typechecks on an iOS build/test run, not the macOS one — verify both when touching `NetworkMetadataCapturer` or `BackgroundTaskCoordinator`.

### App target

```sh
cd ios
xcodegen generate      # regenerate Signals.xcodeproj after editing project.yml
xcodebuild -project Signals.xcodeproj -scheme Signals -destination "generic/platform=iOS Simulator" build
```

The easiest way to connect a device is **QR / deep-link provisioning** (paired with the backend's `GET /admin/provision/qr`, and mirroring the Android flow): the iOS Camera app opens a `signals://connect?base=..&device_id=..&key=..` URL (registered via `CFBundleURLTypes` in `project.yml`), `SignalsApp`'s `.onOpenURL` routes it to `CaptureController.handleConnectURL`, and `applyConnection` adopts the backend-minted device id (`DeviceIdentity.setCurrentDeviceID`), persists the base URL (`ConnectionStore`), and saves the api key — no secret typed on the device. `SyncEngine.deviceID` and `APIClient`'s base URL are runtime-mutable (`updateDeviceID`/`updateBaseURL`) so a scanned credential fully retargets the client; queued rows then upload under the adopted identity (per-row payloads carry no device_id). The link parse is a pure, unit-tested `ConnectLink.parse` in SignalKit — **verify it there, not via `simctl openurl`, which does not deliver custom URL schemes to the simulator** (silently no-ops; only a real device's Camera exercises the full path).

The app also has an in-app provisioning flow (`ProvisioningView`), shown after onboarding whenever no API key is stored: a "paste a pre-provisioned key" path that ships in every build, plus a `#if DEBUG`-only "provision via admin key" path that calls `POST /v1/devices` directly for fast local iteration. It's also reachable any time via the "Device connection" button on the capture screen (`ContentView`), not just on first launch -- needed because a stored key is scoped to whichever backend issued it, so switching backends (e.g. local -> hosted dev) needs re-provisioning even though a key is already present. `DevConfig.apiBaseURL` (`DevConfig.swift`) defaults to the hosted Fly dev backend (`https://signals-api-dev.fly.dev`); override `SIGNALS_API_BASE_URL` / `SIGNALS_API_KEY` via the Xcode scheme's environment variables to point a debug build at a local backend instead (`http://localhost:8080` on the Simulator, the Mac's LAN IP on a real device).

Once "When In Use" location is granted, `ContentView` shows a background-capture banner (`BackgroundUpgradeView`) explaining the "Always" upgrade before triggering the system prompt — a distinct, explicitly-justified ask per the plan, not bundled into the initial request. `CaptureController.locationAuthorizationStatus` tracks the live `CLAuthorizationStatus` via `LocationCapturer.onAuthorizationChange`; `enableBackgroundUpdates()` is only called once "Always" is actually granted.

## Android: build, test

```sh
cd android
JAVA_HOME=$(/usr/libexec/java_home -v 21) ./gradlew :app:assembleDebug   # build APK
JAVA_HOME=$(/usr/libexec/java_home -v 21) ./gradlew :app:testDebugUnitTest   # JVM unit tests
```

Kotlin + Jetpack Compose, single `:app` module. Version stack is pinned to a known-good set that matches the Android Studio install on this machine (AGP 8.13.2, Kotlin 2.0.21, Gradle 8.13, Compose BOM 2024.09.00 — cribbed from `~/AndroidStudioProjects/MyApplication`); the Gradle 8.13 distribution is already cached in `~/.gradle`. minSdk 26, compile/target 36. Package `com.naberconsulting.signals`.

Deliberately lean dependency set to keep the build robust without an IDE to iterate in: **raw `SQLiteOpenHelper`** for the queue (not Room — avoids the KSP annotation-processor version-matching), **`org.json`** for payload/wire JSON (platform-provided, no kotlinx-serialization plugin), **OkHttp** for HTTP, framework **`LocationManager`** (no Play Services). The classifier/model layer is dependency-free so it unit-tests on the plain JVM (`TrackerTagClassifierTest`, ported 1:1 from the iOS `TrackerTagClassifierTests`).

Architecture mirrors iOS deliberately, class-for-class: `CaptureController` (composition root) → `SignalStore` (offline queue, same pending→uploading→uploaded/failed lifecycle incl. stale-upload recovery on init) → `SyncEngine` (single-thread executor, `ConnectivityManager.NetworkCallback` trigger, exponential backoff+jitter, 48h pruning) → `ApiClient`/`UploadBatchBuilder` (wire-identical to the iOS batch contract). Background capture runs via a `location`-typed foreground service (`CaptureService`), the Android analogue to the iOS "Always" background upgrade. `DevConfig.apiBaseUrl` defaults to the hosted Fly dev backend; point at a local backend with `http://10.0.2.2:8080` (emulator loopback alias for the host's localhost).

The five capturers (`capture/`): `LocationCapturer` (also the shared location provider), `BleScanCapturer`, `WifiScanCapturer`, `NetworkMetadataCapturer`, `CellInfoCapturer`. Verified end-to-end on the `Medium_Phone_API_36.0` AVD: the app builds, launches, starts the FGS, and enqueues real `location`/`wifi_scan`/`cell_info`/`network_metadata` records (BLE needs a physical device — the emulator has no BLE peripherals).

**QR / deep-link provisioning (the no-typing connect path).** `MainActivity` registers an intent filter for `signals://connect` (scheme `signals`, host `connect`; `launchMode="singleTask"` + `onNewIntent` so a running app also receives it) and `handleConnectLink` parses `base`/`device_id`/`key` into `CaptureController.applyConnection`, which adopts the backend-minted `device_id` (`DeviceIdentity.setDeviceId`), persists the base URL (`BaseUrlStore`), and saves the api key — no secret typed on the device. `deviceId` is a live `@Volatile var` read by the `SyncEngine.MetaProvider`, so already-queued rows upload under the adopted identity (the queue table stores no per-row device_id). `ApiClient`'s base URL is an `AtomicReference` (`updateBaseUrl`) so a scanned credential can retarget the backend at runtime. Pairs with the backend's `GET /admin/provision/qr`. Verified on the emulator by firing the deep link via `adb` (mind shell quoting — wrap the whole device-side command so the URL's `&` reaches the device shell intact).

**Android captures the identifiers iOS can't.** This is the whole reason the Android client exists alongside iOS. `BleScanCapturer` records the advertiser's real `mac_address` (`ScanResult.device.address`) where iOS only ever sees a session-random UUID; `WifiScanCapturer` enumerates *nearby* APs with their `bssid` (the AP MAC), which iOS has no public API for at all; `CellInfoCapturer` reports neighboring cell identities (MCC/MNC/CI/PCI/TAC). Two **new backend `signal_type`s** carry these — `wifi_scan` and `cell_info` — added to `domain.ValidSignalTypes` (`backend/signals-backend/internal/domain/signal.go`); **the backend must be deployed with those before the hosted dev/prod backends will accept Android batches** (they `400 invalid_signal_type` otherwise). Payloads stay opaque JSON server-side, so no other backend/store/admin changes were needed.

## Non-obvious constraints

- **No real WiFi scanning on iOS.** There is no public API for third-party apps to enumerate nearby SSIDs/BSSIDs (would require an Apple-granted `NEHotspotHelper` entitlement). `NetworkMetadataCapturer` only reports the *currently associated* network plus carrier/radio-tech — it is deliberately named `network_metadata`, not `wifi_scan`, in both the Swift payload type and the backend's `signal_type` column. Don't "fix" this to attempt broader scanning; it isn't available.
- **Background BLE scanning is unreliable for a wildcard scan.** `BLEScanCapturer` accepts an optional `serviceUUIDsToScan` allow-list; per Apple's documented behavior, scanning for all services (`nil`) in the background frequently misses peripherals. If a deployment needs reliable background discovery, it must scan for a curated set of known service UUIDs, not `nil`.
- **BLE peripheral UUIDs are session-random**, not stable hardware identifiers — don't treat `ble_advertisement.peripheral_uuid` as a durable device fingerprint in analysis.
- **Tracker-tag classification (`ble_advertisement.tag_type`) identifies the ecosystem, not the individual tag.** `TrackerTagClassifier` matches known advertisement signatures (Apple Find My manufacturer-data frames, Tile/SmartTag/Chipolo service UUIDs, Google FMDN Eddystone frames); these products rotate their advertised identifiers by design, so sightings can't be joined into "the same tag over time". Note AirTags/Find My accessories advertise *only* manufacturer data — no service UUID — so they are invisible to a background `serviceUUIDsToScan` allow-list scan; only foreground wildcard scanning finds them.
  - **Apple Find My is matched only in the *separated* state, on purpose.** The offline-finding type byte `0x12` is broadcast by *every* Apple device in the Find My network (iPhones/Macs/AirPods near their owner), so matching bare `0x12` flagged huge numbers of ordinary ambient Apple devices as "trackers" (observed: 54 hits / 9 devices in a normal room). The classifier now additionally requires the long "separated" length byte (`>= 0x19`), which carries the rotating public key and indicates a device away from its owner — the genuinely tracker-like case. Both the Swift and Kotlin classifiers share this; the app UIs count **distinct advertiser identities** (MAC on Android, peripheral UUID on iOS), not raw advertisements, and label it "unattended tracker tag(s) detected".
- **`signals` table is partitioned by `captured_at`** with a single `signals_default` catch-all partition for now; there's no monthly-partition creation job yet (noted as a step-13 backend task in the plan, not yet built).
- **Idempotency depends on the client, not the server, generating IDs.** `SignalRecord.id` and each sync batch's `batch_id` are generated at capture/batch-build time (client-side), not at send time — this is what makes retries safe (`ON CONFLICT DO NOTHING` server-side). Don't regenerate these IDs on retry.
- **Port 5432 is taken locally.** A native Homebrew Postgres already listens on `localhost:5432` on this dev machine, ahead of Docker's port-forward for the same port. `deploy/docker-compose.yml` maps the dev Postgres container to host port **5433** to avoid silently talking to the wrong database — keep this in mind if compose files are ever consolidated or `DATABASE_URL` is copy-pasted elsewhere.
- **`Application Support` doesn't exist in a fresh app container.** `CaptureController` creates it (`FileManager...createDirectory`) before opening the GRDB database there — this was a real crash on first launch (SQLite error 14, "unable to open database file") until fixed. Don't remove that `createDirectory` call.
- **`BGTaskScheduler.register` must run before `application(_:didFinishLaunchingWithOptions:)` returns.** That's why `CaptureController` (which registers the background task in its own `init`) is created as a stored property of `AppDelegate` and wired in via `@UIApplicationDelegateAdaptor`, not as a `@StateObject` on the SwiftUI `App` struct — the latter doesn't reliably guarantee that ordering.
- **`simctl uninstall` does not clear `UserDefaults`/`NSUserDefaults` between test runs.** cfprefsd caches an app's preferences domain independent of its container, so a plain uninstall+reinstall (what `xcodebuild test` does) can leave a stale `hasAcknowledgedConsent`/etc. from a previous run, silently skipping onboarding in a UI test even though `AppDelegate`'s `-uitesting-reset` handling calls `UserDefaults.standard.removeObject`. Run `xcrun simctl spawn <device-id> defaults delete com.naberconsulting.signals.app` before each UI test invocation — this was a real, reproduced failure (`ProvisioningFlowUITests` landed straight on the provisioning screen instead of onboarding until this was added), not a hypothetical.
- **The provisioning admin-key path is gated `#if DEBUG`, not a runtime flag.** `ProvisioningView` and `CaptureController.provisionViaAdminKey` compile out of release builds entirely -- the admin key itself is always user-typed, never embedded, but a release build still shouldn't carry the *capability* to call the admin-protected endpoint at all. Don't change this to a runtime toggle (e.g. a settings switch); that would leave the capability shippable, just hidden.
- **`SignalStore` requeues stale `.uploading` rows on init.** `claimBatch` moves rows out of `.pending` before the network call; if the app crashes or is killed mid-upload, those rows have no in-flight tracking once the process exits. `SignalStore.init` calls `recoverStaleUploads()` unconditionally so they aren't silently stuck forever -- don't remove this on the assumption `SyncEngine`'s `markFailed` covers it, since `markFailed` only runs on a definite network response, not a crash.
- **`SyncEngine` prunes uploaded rows itself; nothing else calls `pruneUploaded`.** It runs after every sync pass (`defer` in `runSyncLoop`), deleting `.uploaded` rows older than 48h, so local DB growth is bounded independent of upload volume. `SignalStore.pruneUploaded` is `public` only because `SignalStoreTests` calls it directly -- app code should never need to call it itself.
- **Connectivity-loss/recovery tests use a stubbed `URLProtocol`, not real airplane-mode toggling.** `SyncEngineTests` (`ios/SignalKit/Tests/SignalKitTests/SyncEngineTests.swift`) simulates offline/online transitions deterministically via `StubURLProtocol` injected through `APIClient`'s `session` parameter -- toggling actual simulator/device airplane mode isn't scriptable for CI. If you need to verify real on-device connectivity behavior, that still has to be done manually.
- **`CaptureController` triggers a sync pass on `UIApplication.didBecomeActiveNotification`.** `SyncEngine`'s only other triggers are an `NWPathMonitor` connectivity *change* and the manual "Sync now" button -- if the network never actually drops while the app is backgrounded (the common case), nothing else prompts a sync when the app is reopened, so records captured in the background would sit queued indefinitely. This was a real gap found via on-device background testing (foreground-captured records synced fine; backgrounded ones didn't flush until this observer was added), not a hypothetical. Don't remove the observer on the assumption `NWPathMonitor` already covers "app came back" -- it only fires on state *transitions*.
- **Real-device builds need a bundle ID that isn't already registered to someone else** (`com.signals.app` was taken; the app now ships as `com.naberconsulting.signals.app`) and require an initial USB pairing before Xcode can find the device over WiFi (`Window → Devices and Simulators` → check "Connect via network" once cabled) -- WiFi-only, without ever cabling, the device silently never shows up.
- **`SyncEngine`'s backoff retry no longer blocks the queue with `Thread.sleep`.** A failed pass used to sleep synchronously (up to the 10-minute cap) before releasing `isSyncing`, which meant a manual "Sync now" tap or the foreground trigger arriving during that window silently no-op'd against the `isSyncing` guard -- this was a real, reproduced bug on a real device (repeated taps had zero effect for minutes at a time). Failed passes now call `scheduleRetry(after:)`, which releases `isSyncing` immediately and schedules the retry via `asyncAfter` instead -- don't reintroduce a blocking sleep here.
- **`SyncEngine.onPassCompleted` exists because polling queue state right after `triggerSync()` is unreliable.** `triggerSync()` only dispatches the pass asynchronously and returns immediately, so `CaptureController.syncNow()` calling `refreshPendingCount()` right after it reflected stale, pre-sync state -- on a real device this looked like "Sync now does nothing" even when the upload had actually succeeded. `CaptureController` now also refreshes the count from the `onPassCompleted` callback once the pass actually finishes; don't remove the immediate `refreshPendingCount()` call in `syncNow()` either, since it still gives instant feedback for the common case where nothing was pending.
- **`xcodegen generate` can leave a stale project with no schemes for `Signals`/`SignalsUITests`** if the previous `.xcodeproj` is regenerated in place after certain edits (observed after editing `project.yml` mid-session) -- `xcodebuild -list` then shows only the SPM package schemes (`SignalKit`, `GRDB-Package`). Fix: `rm -rf Signals.xcodeproj` before re-running `xcodegen generate` rather than debugging a partial regeneration.
